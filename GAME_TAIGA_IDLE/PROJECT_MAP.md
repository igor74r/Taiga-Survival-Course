- Папка игры: `GAME_TAIGA_IDLE/`
- Главный документ требований: [GAME_PROMPT_TAIGA_IDLE_SURVIVAL.md](./GAME_PROMPT_TAIGA_IDLE_SURVIVAL.md)

## 3. Где искать конкретную игровую механику СЕЙЧАС

Пока игровой код не разделён на модули. Все перечисленные ниже системы находятся внутри `GAME_TAIGA_IDLE/index.html`.

| Система | Точка входа / ориентир в коде |
|---|---|
| Начальное состояние и сохранение | `fresh()`, `KEY`, загрузка `s`, `save()` |
| Ресурсы и названия предметов | `defs`, `spend()`, `gain()` |
| Время и потребности выживания | `advance(min)` |
| Завершение Idle-работ | `completeJobs(min)` |
| Офлайн-прогресс | `tickOffline()` |
| Отрисовка статусов и экранов | `bar()`, `render()`, `renderView()` |
| Карта и требования открытия | `canExplore()`, массив `places`, `window.explore()` |
| Лагерь и действия | `window.act()` |
| Назначение работ | `window.startJob()` |
| Рецепты и изготовление | единый каталог `recipes`, `window.craft()` |
| Ручное сохранение / сброс | `window.manualSave()`, `window.resetGame()` |
| PWA-регистрация | регистрация Service Worker в конце скрипта |

Названия и расположение функций могут изменяться. При работе проверять актуальный файл, не полагаться только на номера строк из старых отчётов.

## 4. Назначение служебных файлов

- `manifest.webmanifest`: имя приложения, стартовый адрес, ориентация, цвета и иконки PWA.
- `sw.js`: установка, активация, кеширование и сетевые запросы. Кеши изолированы префиксом `taiga-idle-`; fallback на HTML предназначен только для навигации.
- `icon.svg`: исходная векторная иконка.
- `tests/taiga-smoke.test.cjs`: статические contract checks для структуры игровых правил, каталога рецептов и Service Worker. Это НЕ полноценные тесты выполнения механик.
- `.github/workflows/taiga-checks.yml`: запускает проверку наличия файлов, разбирает манифест, извлекает JS и проверяет синтаксис, затем запускает regression checks.

## 6. Правила размещения новых файлов

1. Новые требования и решения по дизайну систем сначала сверять с мастер-промтом.
2. Данные (рецепты, предметы, работы, локации, баланс) хранить отдельно от алгоритмов.
3. Одну механику не дублировать в UI и исполнительном коде: интерфейс должен читать общий каталог данных.
4. Сохранения и миграции держать отдельно от UI.
5. UI не должен самостоятельно менять ресурсы в обход игровых систем.
6. PWA-файлы не смешивать с игровой симуляцией.
7. Тесты размещать в `tests/`; названия тестов должны показывать проверяемую систему.
8. Не создавать пустые папки «на будущее» без задачи и содержимого.
9. Не удалять и не перемещать существующие файлы без проверки ссылок, CI и обновления этой карты.
10. После изменения структуры обновлять этот документ и README.
