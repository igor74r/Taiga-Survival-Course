# Аудит файлов TAIGA — IDLE SURVIVAL

**Дата:** 2026-11-06  
**Ветка:** `main`  
**Объём:** игровой HTML/JS, сохранения, рецепты, карта, Idle-работы, офлайн-расчёт, PWA, CI, smoke/regression checks и документация.  
**Главный источник требований:** [GAME_PROMPT_TAIGA_IDLE_SURVIVAL.md](./GAME_PROMPT_TAIGA_IDLE_SURVIVAL.md).

## Итог

Текущий проект — ранний браузерный вертикальный срез, а не готовая игра и не Android-сборка. Базовый синтаксис JavaScript и статические проверки проходят CI, но функциональная надёжность игровых циклов пока не доказана. До расширения систем рекомендуется устранить перечисленные ниже дефекты и перейти от проверок по текстовым фрагментам к исполняемым тестам.

## Найденные проблемы

### P0 — исправить до дальнейшего расширения

1. **Рецепт факела не выдаёт факел.** В интерфейсе рецепт описан как выдающий `torch: 1`, но в исполняемой таблице `window.craft` награда задана как `fire: 1`. В `advance()` состояние огня затем вычисляется из `fireMinutes`, поэтому предмет факела не появляется в инвентаре.  
   Файл: `index.html`, строки с рецептами в `renderView()` и `window.craft`.

2. **Дублирование данных рецептов.** Список рецептов для интерфейса и список для исполнения объявлены независимо. Это уже привело к расхождению. Нужен единый каталог рецептов, из которого строятся карточки, проверка стоимости и выдача результата.

3. **Разведение костра не проверяет успешность списания ресурсов.** `window.act('fire')` вызывает `spend(...)`, но не проверяет возвращаемое значение. При прямом вызове функции без достаточных ресурсов огонь всё равно активируется. Исправить на ранний выход при неуспешном списании и добавить тест.

### P1 — высокий приоритет

4. **Проверки игрового процесса не являются полноценными игровыми тестами.** `tests/taiga-smoke.test.cjs` проверяет наличие подстрок в HTML. Такие проверки могут пройти, даже если действие не работает во время выполнения. Нужны тесты поведения: изменение ресурсов, успешный/неуспешный крафт, таймер огня, завершение работы, блокировка/разблокировка карты, офлайн-прогресс и восстановление сохранения.

5. **Service Worker удаляет все кеши origin.** В обработчике `activate` удаляются все Cache Storage записи, кроме `taiga-idle-v1`. Если на том же origin размещены другие приложения, их кеши могут быть удалены. Удалять следует только кеши с собственным префиксом TAIGA.

6. **Неправильный fallback в Service Worker.** При ошибке любого GET-запроса возвращается `./index.html`, даже если запрашивались иконка, манифест или иной ресурс. Fallback на HTML должен применяться только к навигационным запросам; для остальных запросов нужно корректно вернуть ошибку/ответ без подмены типа контента.

7. **Нет безопасной обработки ошибок сохранения.** Чтение localStorage частично защищено, но `save()` вызывает `localStorage.setItem` без обработки исключений. При недоступном хранилище или переполнении квоты сохранение может сорвать действие и дальнейшее обновление интерфейса. Нужна обработка ошибки и понятное предупреждение игроку.

8. **Данные сохранения не проходят полноценную валидацию.** Поверх сохранения накладываются значения по умолчанию, но произвольные типы и диапазоны для ресурсов, времени, состояния работ и версии сохранения не проверяются. Нужна схема проверки и миграции версии.

### P2 — системные и продуктовые пробелы

9. **Визуальная погода пока декоративна.** На экране меняется подпись по времени суток, но нет отдельной модели температуры/осадков/ветра и их реального влияния на выживание.

10. **Работы и офлайн-симуляция упрощены.** Работа выдаёт фиксированную награду; нет риска, износа инструмента, отмены, прерывания, расхода припасов или влияния погоды. Это допустимо для прототипа, но не соответствует глубине мастер-промта.

11. **Нет полноценной модели экспедиции.** Точки карты открываются последовательностью, но нет маршрута, подготовки снаряжения, длительности похода, расхода запасов, угроз, событий в пути и результата возвращения.

12. **Есть неиспользуемые/заделочные поля состояния.** Например, `crafted` и `story` присутствуют в новом сохранении, но пока не связаны с завершёнными игровыми системами. Их следует либо подключить, либо документировать как зарезервированные поля.

13. **Документация отстаёт от кода.** README всё ещё описывает отсутствие автоматизированных тестов, хотя CI уже запускает статические regression checks. README следует обновить и точно описать границы этих проверок.

14. **Вся игра находится в одном HTML-файле.** Для самого первого прототипа это удобно, но с ростом числа систем усложнит тестирование и поддержку. После стабилизации механик рекомендуется выделить конфигурации, симуляцию, сохранения, UI и PWA-обвязку в отдельные модули, не меняя платформу без необходимости.

## Что уже подтверждено

- JavaScript проходит синтаксическую проверку в GitHub Actions.
- JSON-манифест проходит JSON.parse.
- CI проверяет наличие viewport, манифеста и основных файлов.
- CI запускает `tests/taiga-smoke.test.cjs`.
- Успешный запуск CI: [run 42126993623](https://github.com/igor74r/Taiga-Survival-Course/actions/runs/42126993623).

**Важно:** успешный CI подтверждает только реализованные проверки. Он не доказывает корректную работу игры в браузере, PWA-установку или работу на физическом Android-устройстве.

## План исправлений

1. Свести рецепты к единому каталогу и исправить выдачу факела.
2. Сделать все действия атомарными: сначала проверить и списать стоимость, затем менять состояние.
3. Исправить область удаления кешей и навигационный fallback в Service Worker.
4. Добавить безопасную запись сохранений, валидацию и миграцию версии.
5. Перейти от текстовых assertions к исполняемым тестам игровых функций.
6. Обновить README и повторить CI.
7. После стабилизации — тестирование в браузере Android и только затем продолжение экспедиций/производства.

## Ограничения аудита

Аудит выполнен статически по текущим файлам ветки `main`. Реальный запуск в браузере, проверка на физическом Android-устройстве, нагрузочные тесты, тесты интерфейса касанием и проверка установки PWA в ходе этого аудита не выполнялись.
